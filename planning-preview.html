Portfolio requirements

Version 0.1 · Planning draft · 7 October 2026

1. Purpose and audience

The portfolio should help a visitor understand who Palak is, see evidence of engineering ability, explore relevant projects, and find a contact channel. Aim for a visitor to identify Palak's focus and open a featured project within roughly 30 seconds.

Primary audience, provisionally: recruiters and engineering teams. Secondary audience: collaborators and people interested in the projects. The emphasis can change without changing the core architecture.

User stories:

  • As a recruiter, I can scan the homepage, open a relevant case study, and find a resume or contact link when supplied.
  • As an engineer, I can understand a project's problem, architecture, tradeoffs, and limitations, then inspect its source.
  • As a collaborator, I can see Palak's interests and find a reliable way to reach out.
  • As the owner, I can add or reorder a project by editing content files without modifying the page layouts.

5. Case-study content contract

Each published project needs:

  1. Title, stable slug, one-sentence summary, categories, technologies, and an accurate status.
  2. The problem and who benefits from solving it.
  3. Palak's role and contribution, distinguishing personal work from team or third-party work.
  4. One authentic screenshot or a diagram clearly identified as a diagram.
  5. The approach, architecture, and one or two meaningful engineering decisions.
  6. Outcomes supported by evidence; qualitative outcomes are acceptable when measurements are unavailable.
  7. Limitations and lessons learned.
  8. Source link when public, optional live demo, and optional additional screenshots.

A portfolio hosts descriptions, images, diagrams, and links. Running the projects themselves is separate work. Existing Python/Streamlit applications, local LLMs, Windows tooling, and GPU workloads will retain their own runtime and hosting arrangements. Projects without a public demo can still have strong case studies.

7. Responsive behavior

Use content-driven breakpoints, starting near 640 and 1024 px.

  • Mobile: one column, compact header, accessible menu, full-width project visuals, wrapping actions.
  • Tablet: two-column cards; stack the hero if the text becomes cramped.
  • Desktop: split hero, three-column cards, optional case-study section sidebar.
  • Do not reorder content in a way that makes keyboard order differ from the visual reading order.
  • Maintain touch targets of approximately 44 × 44 px and room between adjacent controls.
  • Sticky navigation must not obscure anchor targets or focused elements; apply scroll margins.

8. Interaction and accessibility

  • Primary actions have clear labels: Explore projects, Read case study, View source, Contact.
  • Focus uses a visible high-contrast outline; skip-to-content link is available.
  • Mobile menu uses a labelled button and expanded state, closes on Escape, and restores focus appropriately.
  • Use short CSS transitions, approximately 150–220 ms. Motion must not hide content before scripts load.
  • Respect reduced-motion preferences and avoid scroll-jacking, parallax, and continuous decorative motion.
  • Copy email reports success or failure through an accessible status message. The email link remains available if clipboard access fails.
  • Images include meaningful alt text or empty alt text when decorative; captions clarify what the visual demonstrates.
  • Heading structure and link names communicate destination and purpose.
  • Unknown routes provide Home and Projects links; a missing image keeps its reserved space and an honest fallback.

9. Assets and content rules

Prefer real screenshots from the projects and existing project artwork after verifying usage rights. Crop them consistently but preserve the application's meaning. Do not use generated screenshots to imply functionality that does not exist.

The favicon uses the approved monogram and palette. Launch includes Open Graph title/description metadata; a custom social preview image can be added if requested. No unsupported employers, dates, degrees, user counts, or performance claims may appear.

10. Design review criteria

The homepage should identify Palak, show a clear route to the work, and feel coherent at mobile and desktop widths. Project cards must communicate differences between projects. Case studies should be comfortable to read and contain concrete engineering detail. Missing optional content must not leave empty sections, dummy links, or unexplained placeholders in the published version.

5. Rendering and static output

Pre-render all published routes from the same content manifest used by the project index. Each route gets its own title, description, canonical address, and visible project content in HTML. Optional browser enhancements handle filtering and clipboard behavior after hydration.

Expected publish directory: build/client for the proposed React Router build. Confirm this with the selected releases. A finalization step generates sitemap.xml, robots.txt, and 404.html, and validates that every published slug has an HTML document. Keep any build-time server bundle outside the upload directory.

Set Cloudflare asset handling to not_found_handling: "404-page" and html_handling: "drop-trailing-slash" for the proposed URL convention. Publish a real 404.html and test that direct requests to unknown routes return HTTP 404. Avoid a catch-all SPA rewrite that would turn unknown project URLs into success responses. See Cloudflare static generation and 404 routing.

Test both direct requests and browser navigation: generated .data files, project paths, trailing-slash normalization, and unknown slugs. Canonical URLs and sitemap URLs must use the same convention.

8. Cloudflare deployment plan

Recommended: deploy the pre-rendered output through Workers Static Assets. Cloudflare supports static files without a custom application Worker script; its React + Vite guide also covers the broader frontend/API setup. We only need the static delivery capability at launch. See Static Assets.

Deployment configuration will identify the portfolio Worker, compatibility date, build/client asset directory, and static routing rules. Use repository-based builds with a committed lockfile. Build command: npm run build; deployment command: npx wrangler deploy. Configure nonproduction branches for preview/version URLs and main for production according to the current Workers Builds controls. See Workers Builds.

Domain sequence:

  1. Confirm control of palakdebpatra.com, an active Cloudflare zone, account access, and any existing web records.
  2. Deploy and review the portfolio at its Cloudflare preview address.
  3. Attach palakdebpatra.com as the Worker's Custom Domain. Cloudflare handles associated DNS/certificate setup; inspect any conflicting existing web record before replacing it.
  4. Set up a proxied DNS record and a permanent redirect for www.palakdebpatra.com to the apex, preserving path and query string.
  5. Verify certificate activation, HTTP-to-HTTPS behavior, apex responses, redirect behavior, static assets, and direct detail routes.
  6. Preserve unrelated MX/TXT records and existing services. Do not assume Cloudflare DNS registration alone means the portfolio is already hosted.

The Custom Domain and www redirect requirements are described in Cloudflare's Custom Domains documentation. Nameserver/account status and existing records remain unverified.

Alternative: Cloudflare Pages can also publish static Vite output with Git integration. For this proposed architecture, use npm run build and build/client; a plain Vite React build would normally use dist. Attaching an apex domain through Pages requires that domain to be a zone in the same Cloudflare account with the appropriate nameservers. See Pages Vite deployment and Pages custom domains. Keep one deployment target rather than maintaining both.

9. Release and maintenance

Store the last known-good deployment/version identifier and document rollback through Cloudflare. Content updates follow edit → local validation → preview → production. Keep asset caching appropriate for fingerprinted files, allow HTML to update promptly, and review security headers against the actual asset sources.

No paid service is a prerequisite in this design. Check applicable hosting limits and domain renewal costs at deployment time rather than promising unlimited free hosting. Demo services, GPU hosts, analytics, and email delivery would have separate requirements and costs if added.
